# Translations (English / Czech)

The public site is bilingual. Czech is the primary audience language, English is
the fallback and the source text.

## How it works

Templates keep their **English text** and tag it with a key:

```html
<h2 data-i18n="about.mission">Our Mission</h2>

<a class="nav-link" href="..." data-i18n-html="nav.board">
    <i class="bi bi-clipboard-check"></i> Board
</a>

<input data-i18n-placeholder="wall.ph_add_a_comment" placeholder="Add a comment...">
```

`app/static/js/i18n.js` holds the dictionary:

```js
var TEXTS = {
    "en": { "nav.board": "<i class=\"bi bi-clipboard-check\"></i> Board", ... },
    "cs": { "nav.board": "<i class=\"bi bi-clipboard-check\"></i> Výbor", ... }
};
```

On load, `LANG.init()` picks the language (saved choice, else the browser's
`navigator.languages`) and rewrites the marked elements. `LANG.toggle()` — the
EN/CS button in the navbar — switches and remembers the choice in `localStorage`.

Keeping the English in the template is deliberate: the page is readable without
JavaScript, and a key with no translation simply stays English instead of
rendering an empty string.

## Which attribute to use

| Attribute | Effect | Use when |
|---|---|---|
| `data-i18n` | sets `textContent` | the element contains **text only** |
| `data-i18n-html` | sets `innerHTML` | the element contains an icon, `<strong>`, `<br>` or a link |
| `data-i18n-placeholder` | sets `placeholder` | form inputs |
| `data-i18n-title` | sets `title` | tooltips |
| `data-i18n-aria-label` | sets `aria-label` | accessibility labels |
| `data-i18n-value` | sets `value` | submit buttons, options |

**`data-i18n` on an element containing an icon deletes the icon**, because
`textContent` replaces all children. Always prefer `data-i18n-html` for buttons
and links that carry a Bootstrap icon, and include the `<i>` tag in the
translation value.

## Adding a string

1. Add the key to the template in English:
   `<p data-i18n="mypage.intro">Some new text</p>`
2. Add the same key to **both** `en` and `cs` in `app/static/js/i18n.js`.
   The `en` value must match the template text.
3. Check it:

   ```bash
   venv/bin/python scripts/i18n_audit.py --strict
   ```

   This lists, per template, how many marked strings have no Czech, flags keys
   that are used but missing from the dictionary, and reports dictionary entries
   that no template references any more.

Key naming: `<page>.<short_description>`, e.g. `about.key_features`,
`nav.ideas_wall`, `method.annualized_return_cagr`. Keys are shared between pages
when the text is identical — but **never** give one key to two different English
strings, and never share a key between an icon version and a plain version of a
label (use `nav.research` vs `footer.research`).

## Adding a language

1. Add the language code to `supported` in `app/static/js/i18n.js`.
2. Add a block to `TEXTS` with the same key set.
3. Teach `LANG.detect()` the language tag(s) to match (it currently maps `cs*` to
   Czech and everything else to English).
4. `LANG.toggle()` switches between `en` and `cs` — extend it if you add a third
   language, or replace the button with a dropdown.

## Gotchas

- **`window.LANG` must be defined in exactly one place** — `static/js/i18n.js`.
  It used to be defined in `js/app.js` as well, and because `app.js` loads later
  (end of `<body>`) it silently replaced the object holding the dictionary:
  `LANG.texts` and `LANG.apply` became `undefined` and the toggle did nothing at
  all. `tests/test_i18n.py` now enforces the single definition.
- **Don't translate sentence fragments.** All content is licensed for translation
  only when it comes from a single, complete element — never a `<strong>` or a
  link inside a paragraph. Czech word order differs from English, so fragment
  translation leaves the connecting prose in English and reads as nonsense.
- **Don't put a key on an element that wraps a Jinja expression** (for example a
  `title` built from a variable). The translation would freeze a dynamic value.
  Handle those in the template only.
- An element with `data-i18n` must not contain another marked element — the outer
  replacement would shadow the inner one.

## Checking your work

```bash
# coverage / missing / stale keys
venv/bin/python scripts/i18n_audit.py --strict --show-missing

# template markup safety (no mangled tags, no icon-clobbering)
venv/bin/python -m pytest tests/test_i18n.py tests/test_templates.py -q
```

`tests/test_i18n.py` also keeps a `FULLY_TRANSLATED` list of every public page;
if one of them starts falling back to English, the suite fails.

For checks that need a real DOM (does the toggle actually work, does Czech
actually render, is any markup mangled), render pages and run the jsdom tests:

```bash
npm install jsdom
for p in / /about /methodology /wall /privacy /terms /blog/ /auth/login; do
    f=$(echo "$p" | tr '/' '_'); curl -s "http://127.0.0.1:5001$p" > "/tmp/page$f.html"
done
node tests/js/i18n.test.js /tmp/page_*.html
node tests/js/chart_panels.test.js /tmp/page_.html   # chart rendering
```

One thing to know when writing such a check: `js/app.js` decorates links at
runtime (it adds `data-cursor-hover="true"` for the custom cursor), so a
rendered element's `innerHTML` legitimately differs from the dictionary by
attributes. Compare tag names, nesting and text, not attributes.

## Size

`i18n.js` is about 120 KB unminified (~30 KB gzipped) and is loaded on every
page, including the analyst dashboard where no translated content appears. It is
cacheable and fine for now. If it ever becomes a problem, split the per-page
keys into separate files, or fetch the `cs` block lazily only when the language
is Czech.
